# Отправка JSON-ответов

В этом блоке мы изменим наше API таким образом, чтобы ответы отдавались в формате JSON. Давайте переключимся на ветку `4-sending-JSON-responses`.

И начнем мы с небольшого теоретического блока.
На высоком уровне в Go есть два способа кодировать данные в JSON:

(Слайд №1)
- использовать функцию `json.Marshal()`;
- использовать тип `json.Encoder`.

В рамках этого проекта мы будем использовать первый вариант — `json.Marshal()`, а точнее `json.MarshalIndent`.
Эта функция по смыслу аналогична `json.Marshal()` (обертка, в теле которой вызывается `json.Marshal()`), но предназначена для получения более удобочитаемого результата.
То есть она просто форматирует итоговый JSON, добавляя отступы.
Принцип работы `json.MarshalIndent` довольно прост:
вы передаете ей значение того или иного типа Go в качестве аргумента,
а она возвращает JSON-представление этого значения в виде среза `[]byte`.

Сигнатура функции выглядит так:

(Слайд №2)
```go
func json.MarshalIndent(v any, prefix string, indent string) ([]byte, error)
```
Параметр `v` имеет тип `any`.
Это означает, что в функцию можно передать значение практически любого типа Go.

## Дополнительная информация

Теперь снова сделаем небольшую теоретическую паузу.

На данном этапе мы закодировали в JSON тип `map`.
Но Go поддерживает кодирование и многих других встроенных типов.

Давайте посмотрим на таблицу, демонстрирующую, как именно различные типы кодируются в JSON.

(Слайд №3)

| Тип Go                                              | ⇒ | Тип JSON                             |
| --------------------------------------------------- | - | ------------------------------------ |
| `bool`                                              | ⇒ | логическое значение JSON             |
| `string`                                            | ⇒ | строка JSON                          |
| `int*`, `uint*`, `float*`, `rune`                   | ⇒ | число JSON                           |
| массивы, ненулевые (`non-nil`) срезы                | ⇒ | массив JSON                          |
| структуры, ненулевые (`non-nil`) карты              | ⇒ | объект JSON                          |
| `nil`-указатели, значения интерфейсов, срезы, карты | ⇒ | `null`                               |
| `chan`, `func`, `complex*`                          | ⇒ | не поддерживаются                    |
| `time.Time`                                         | ⇒ | строка JSON в формате RFC 3339       |
| `[]byte`                                            | ⇒ | строка JSON, закодированная в Base64 |

Тут стоит обратить особое внимание на пару моментов:

1. Значения `time.Time` (которые внутри представляют собой структуру) кодируются не как JSON-объекты, а как строки в формате RFC 3339. Это происходит потому, что для этого типа реализован специальный метод, который определяет, как именно преобразовывать значение в JSON. Мы коснемся этой темы немного дальше, а пока просто обращаю на это внимание.
2. `[]byte` кодируется не как массив чисел JSON, а как строка в кодировке Base64.

(Слайд №4)

Например, следующий срез байтов:
```go
[]byte{'h','e','l','l','o'}
```
будет представлен в JSON как строка:
```text
"aGVsbG8="
```
Также стоит отметить еще несколько важных моментов:

- Кодирование вложенных типов полностью поддерживается. Например, срез структур будет преобразован в массив объектов JSON.
- Каналы (`chan`), функции (`func`) и комплексные числа (`complex`) кодировать нельзя. Попытка сделать это приведет во время выполнения к ошибке `json.UnsupportedTypeError`.
- Любые указатели кодируются как значения, на которые они указывают.

## cmd/demo-api/errors.go

Следующим шагом давайте посмотрим на файл `cmd/demo-api/errors.go`, в котором описан вызываемый в `healthcheckHandler` метод `app.serverErrorResponse`.

Тут мы видим пять методов.
Давайте выясним их назначение.

1. Метод `serverErrorResponse` используется, когда приложение сталкивается с непредвиденной проблемой во время выполнения.
   Он записывает подробное сообщение об ошибке в лог, затем с помощью метода `errorResponse` отправляет клиенту JSON-ответ со статусом `500 Internal Server Error` (содержащий обобщенное сообщение об ошибке).

2. Метод `errorResponse` является вспомогательным методом для отправки клиенту сообщений об ошибках в формате JSON с указанным кодом состояния.
   Обратите внимание, что для параметра `message` используется тип `any`, а не `string`, поскольку это дает нам больше гибкости в выборе значений, которые можно включать в ответ.
   В сущности, в теле метода мы просто оборачиваем `message` в `envelope`, а после записываем ответ с помощью вспомогательного метода `writeJSON`.
   Если он вернет ошибку, записываем ее в журнал и, в качестве резервного варианта, отправляем клиенту пустой ответ со статусом `500 Internal Server Error`.

3. Метод `logError` является вспомогательным методом для записи сообщения об ошибке в логи вместе с методом текущего запроса и его URL.

4. Метод `notFoundResponse` используется для отправки клиенту JSON-ответа со статусом `404 Not Found`.

5. Метод `methodNotAllowedResponse` используется для отправки клиенту JSON-ответа со статусом `405 Method Not Allowed`.

## cmd/demo-api/middleware.go

Для этого перейдем в файл `cmd/demo-api/middleware.go`.
Тут мы видим метод `recoverPanic`, который возвращает функцию, преобразованную адаптером `http.HandlerFunc` и теперь удовлетворяющую интерфейсу `http.Handler`.

В теле этой функции мы объявляем и вызываем отложенную функцию.

### middleware

В качестве дополнения дам чуть более развернутое описание по этой теме.
Как я уже показывал ранее, у нас есть созданный веб-сервер в файле `cmd/demo-api/main.go`.

(Слайд №5)
```go
srv := &http.Server{
    Addr:         fmt.Sprintf(":%d", cfg.port),
    Handler:      app.routes(), <======
    IdleTimeout:  time.Minute,
    ReadTimeout:  5 * time.Second,
    WriteTimeout: 10 * time.Second,
    ErrorLog:     slog.NewLogLogger(logger.Handler(), slog.LevelError),
}
```

И в его поле `Handler` устанавливается результат работы `app.routes`.
То есть там установлена одна функция, являющаяся началом цепочки обработчиков.
В нашем случае это будет именно результат работы `app.recoverPanic`,
которая возвращает наш middleware, или первый обработчик.

Внутри него сначала регистрируется `defer`, а затем вызывается следующий обработчик через `next.ServeHTTP`.
В нашем случае это маршрутизатор.
То есть на этапе запуска бинарника будет инициализирован веб-сервер, и в нем — начало цепочки обработчиков.

Визуально можно воспринимать так:

(Слайд №6)
```text
http.Server
      │
      ▼
recoverPanic
      │
      ▼
httprouter
      │
      ▼
конкретный handler
```

А далее для каждого запроса будет создаваться отдельная горутина, в которой сначала начнет выполняться middleware, а затем `router`.

Как результат, в каждой горутине, или в каждом запросе, если произойдет вызов `panic`, начнется размотка стека, то есть будут вызваны все зарегистрированные `defer`-функции.
А значит, мы сможем перехватить эту панику, не дав упасть всему приложению.

Опять же, если упростить тему для визуального восприятия, то каждый запрос приведет к порождению отдельной горутины, словно бы «маленького процесса» внутри реального процесса, то есть запущенного бинарника `demo-api`:

(Слайд №7)
```text
Процесс (demo-api)
│
├── goroutine #1 (обработка запроса A)
├── goroutine #2 (обработка запроса B)
├── goroutine #3 (обработка запроса C)
└── goroutine #4 (обработка запроса D)
```
Но, естественно, это не полноценные процессы, а легковесные потоки.
Если в одной горутине происходит `panic`, то получается примерно такая картина:

(Слайд №8)
```text
Процесс demo-api
│
├── goroutine #1 ──> recoverPanic ──> router ──> handler ──> panic!!!
│                                                         |
│                                                         v
│                                              defer + recover
│                                                         |
│                                                         v
│                                              вернуть HTTP 500
│                                                         |
│                                                         v
│                                           goroutine завершилась
│
├── goroutine #2 ──> продолжает работать ──> ...
│
└── goroutine #3 ──> продолжает работать ──> ...
```
Так вот, если в таком "мини-процессе" не перехватить панику, то это завершит весь реальный процесс `demo-api`.

Хорошо, с этим всё, и идем дальше.

## `internal/data/runtime.go`

И в завершение давайте посмотрим на именованный тип `Runtime`.

Для этого перейдем в файл `internal/data/runtime.go`.
Тут снова нужно сделать небольшое теоретическое отступление.

Когда Go кодирует какой-либо тип в JSON, он проверяет, есть ли у этого типа метод `MarshalJSON` (то есть удовлетворяет ли этот тип интерфейсу `json.Marshaler`). Если такой метод существует, Go вызывает его, чтобы определить, как должен быть закодирован этот тип.
Если же у типа нет метода `MarshalJSON()`, Go попытается закодировать его в JSON, используя собственный внутренний набор правил.

Например, вы можете увидеть это в действии, если посмотрите исходный код типа `time.Time`. Внутри он на самом деле представляет собой структуру, но у нее есть метод `MarshalJSON`, который выводит значение в формате RFC 3339. Именно этот метод вызывается всякий раз, когда значение `time.Time` кодируется в JSON.

Так вот, мы тут делаем то же самое, но для нашего типа `Runtime`.
Также объявляем метод `MarshalJSON`, в котором определяем, как именно будет кодироваться в JSON значение этого типа.
То есть, по сути, преобразовываем число к строке и добавляем постфикс `mins`.
После чего заключаем результат в кавычки и возвращаем преобразованную в `[]byte` строку.

Это действие не является необходимым, а реализовано исключительно для демонстрации функционала.
