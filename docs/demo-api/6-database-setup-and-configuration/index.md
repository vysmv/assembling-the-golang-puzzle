## Подключение к базе из нашего кода

Для того чтобы работать с базой данных из нашего приложения, необходимо использовать специальный драйвер,
который выступает в роли «посредника» между `Go` и самой базой данных.

Существует множество таких драйверов, но мы будем использовать `pq`.

Соответственно, его нужно установить.
Для этого я уже выполнил команду:

(Слайд №1)
```bash
go get github.com/lib/pq@v1
```

Если вы тестируете этот код на своём компьютере, также выполните её в корне проекта и не забудьте после этого пересобрать проект. Для этого сначала в терминале, где он запущен, нажмите `Ctrl+C`, а затем выполните команду:

```bash
docker compose up --build
```

Хорошо, идём дальше.

Для подключения к базе данных из нашего кода нам также понадобится `DSN (Data Source Name)`.

В нашем файле `.env` есть переменная `DB_DSN`.

По сути, это строка, содержащая необходимые параметры подключения.
Формат `DSN` зависит от используемого драйвера базы данных (он должен быть описан в документации драйвера).

В нашем случае для драйвера `pq` формат будет следующим:

(Слайд №2)

```text
DB_DSN="postgres://vysmv:secret@postgres/demo_api?sslmode=disable"
```

Где:
- scheme    = postgres
- user      = vysmv
- password  = secret
- host      = postgres
- database  = demo_api

## `cmd/demo-api/main.go`

Что тут изменилось?

1. В блок `import` мы добавили драйвер `_ "github.com/lib/pq"`.

   Обратите внимание, что в качестве алиаса для этого пакета мы используем нижнее подчёркивание.
   Это связано с тем, что мы не используем пакет драйвера напрямую в нашем коде. Он используется «под капотом».

   Если упростить, то во время запуска бинарного файла до выполнения функции `main()` `Go` инициализирует импортированный пакет `github.com/lib/pq`. В процессе инициализации автоматически выполняется его функция `init()`. Внутри `init()` драйвер регистрирует себя в пакете `database/sql`. После этого пакет `database/sql` знает, какой драйвер нужно использовать.

   Если импортировать пакет без алиаса `_`, то будет ошибка на этапе компиляции.

2. Также можно увидеть, что мы импортировали ещё два пакета из стандартной библиотеки:
   - `"context"`
   - `"database/sql"`

3. Далее мы изменили структуру `config`, добавив в неё новое поле `db` с типом анонимной структуры, у которой четыре поля:
   - `dsn` типа `string`,
   - `maxOpenConns` типа `int`,
   - `maxIdleConns` типа `int`,
   - `maxIdleTime` типа `time.Duration`.

4. Следующим шагом я вынес код чтения флагов командной строки в отдельную функцию, чтобы разгрузить функцию `main`.

Теперь весь код, считывающий значения флагов и устанавливающий значения конфигурации, будет сосредоточен здесь — `setConfig`.

В теле функции `setConfig` мы можем увидеть, что появились новые флаги, которые готово принимать наше приложение:

- `db-dsn`: здесь мы даём возможность переопределить значение `DSN` при запуске бинарника.
  Но по умолчанию оно читается из переменной окружения.

А также появились ещё три новых флага.

Чтобы понять их назначение, я сделаю небольшое теоретическое отступление.

Далее по коду мы будем создавать пул соединений с базой данных.
Для этого используется пакет `database/sql` из стандартной библиотеки.
То есть это что-то вроде менеджера, через которого мы будем выполнять запросы.

Этот пул имеет тип `sql.DB`.

Так вот, в нём есть соединения двух видов:

(Слайд №3)

- используемые (in-use);
- неактивные (idle).

Соединение помечается как используемое, когда вы выполняете с его помощью
какую-либо операцию с базой данных, например выборку строк.
После завершения операции соединение снова помечается как неактивное.

Когда мы инициируем выполнение какого-либо действия с базой данных,
сначала проверяется, есть ли в пуле свободные неактивные соединения.
Если такое соединение найдено, Go повторно использует его и помечает
как используемое на время выполнения операции.
Если же свободных соединений нет, в пуле создаётся новое соединение.

Так вот, этот пул соединений имеет четыре метода для настройки своего поведения:

(Слайд №4)

- `SetMaxOpenConns()` позволяет установить верхний предел для
  количества открытых соединений (используемых + неактивных).

По умолчанию количество открытых соединений не ограничено.
Но оставлять этот параметр без ограничений не всегда является идеальным решением,
так как при высокой нагрузке это может сделать базу данных недоступной для других сервисов.

Поэтому мы будем устанавливать собственное значение для общего количества соединений с базой данных из приложения.

(Слайд №5)

- `SetMaxIdleConns()` устанавливает верхний предел для количества неактивных соединений в пуле.

По умолчанию максимальное количество неактивных соединений равно 2.
Теоретически увеличение количества неактивных соединений повышает производительность,
поскольку уменьшает вероятность того, что новое соединение придётся создавать с нуля,
а значит, позволяет экономить ресурсы.

Однако важно понимать, что поддержание неактивного соединения тоже имеет свою цену.
Оно занимает память, а также существует вероятность того, что соединение станет непригодным для использования, если будет слишком долго простаивать.

Поэтому мы также ограничим это значение.

(Слайд №6)

- `SetConnMaxLifetime()` устанавливает максимальное время,
  в течение которого соединение может повторно использоваться.

По умолчанию максимальное время жизни отсутствует, и соединения используются бесконечно.
Но мы не будем менять этот параметр.

(Слайд №7)

- `SetConnMaxIdleTime()` ограничивает максимальное время, в течение которого соединение может оставаться неактивным, прежде чем будет признано устаревшим.

По умолчанию ограничение отсутствует.
Эта настройка очень полезна, поскольку позволяет установить относительно высокий предел на количество неактивных соединений, но при этом периодически освобождать ресурсы, удаляя соединения, которые уже фактически не используются.

В общем-то три следующих флага:

- `db-max-open-conns`;
- `db-max-idle-conns`;
- `db-max-idle-time`

позволят переопределять значения по умолчанию на этапе запуска бинарного файла.

Хорошо, с теоретическим отступлением всё, и возвращаемся к обзору изменений.

5. Далее мы вызываем вспомогательную функцию `openDB()`, чтобы создать
пул подключений, передавая ей структуру `config`. Если она возвращает
ошибку, записываем её в лог и немедленно завершаем приложение.

6. После этого откладываем вызов `db.Close()`, чтобы пул подключений был закрыт
перед завершением функции `main()`.

7. Пишем в лог сообщение `"database connection pool established"` об успешном создании пула соединений.

8. Вносим правку в работу с переменной `err`. То есть заменяем `:=` на `=`, так как мы её уже не инициализируем, а переопределяем.

9. Объявляем функцию `openDB()`, которая будет возвращать тот самый пул соединений, о котором мы говорили.

Давайте посмотрим, что именно происходит в теле этой функции.

## `func openDB(cfg config) (*sql.DB, error)`

- Первым делом мы используем `sql.Open()` для создания пустого пула подключений, передавая `DSN` из структуры `config`.
- Следующим шагом мы используем те методы пула соединений, которые только что обсудили, и передаём в них значения из конфигурации.
- Далее создаём контекст с таймаутом в 5 секунд.
- После чего используем `PingContext()` для установки нового соединения с базой данных, передавая созданный выше контекст. Если соединение не удастся установить в течение 5 секунд, метод вернёт ошибку. При возникновении этой или любой другой ошибки мы закрываем пул подключений и возвращаем ошибку. По сути, это просто проверка доступности базы данных с пятисекундным ограничением по времени.
- А в конце просто возвращаем указатель на пул соединений `*sql.DB`.
