# Рабочее окружение

## Общая картина

Следующим шагом посмотрим на рабочее окружение.
Для этого переключимся на ветку `2-getting-started`.
Как я и сказал ранее, мы будем использовать докер.
Демонстрировать процесс его установки я не буду, так как информации о том, 
как его установить, достаточно практически для любой популярной ОС.

Так что давайте сразу сделаем обзор первой стадии проекта.

Я предполагаю, что большая часть из вас знает, что такое докер 
и какие задачи он решает, но если есть и те, кто не совсем понимает, 
что к чему, то дам короткое пояснение.

В общем, при разработке какого-то приложения требуется, например, 
иметь установленными сам интерпретатор или компилятор, базу данных и, 
возможно, еще набор всяких сервисов.

Для нас, как для разработчиков, существует несколько путей того, как можно этого добиться:

1. (Слайд №1) Устанавливать все это на свой компьютер.
   Это плохой вариант, потому что мы можем разрабатывать параллельно два, 
   три или пять приложений.
   В итоге будет свалка, путаница с версиями, и это приводит к такому эффекту, 
   который называется «на моем компьютере работает, а что там у вас — я не знаю».

2. (Слайд №2) Использовать виртуальные машины. Например, это связка VirtualBox + Vagrant.
   То есть внутри вашей ОС будет ряд полноценных виртуальных ОС, 
   и окружение для работы можно поднимать там.
   Но это ресурсоемко. Хотя однозначно лучше, чем первый вариант.

3. (Слайд №3) Использовать докер. На данный момент это наиболее распространенная практика.
   По смыслу это выглядит примерно так: есть две ключевые сущности: образ и контейнер.

Представьте, что где-то кто-то установил, например, на чистую ОС Debian 13 Trixie 
язык Go версии 1.26.3 и набор утилит, нужных для работы.

А затем сделал слепок файлов, необходимых для работы этих программ.
Так получился образ файловой системы с установленным Go и необходимыми утилитами.
Назовем его, например:

(Слайд №4)

```text
golang:1.26.3-trixie
```

Это получился образ.

Далее мы устанавливаем на нашу реальную ОС докер.
Он позволяет создавать внутри нашей ОС изолированные контейнеры на 
основе созданного ранее образа.

То есть реальная ОС одна — та, что установлена на вашем компьютере.
И для каждого приложения, которое вы разрабатываете, создается один 
или более контейнеров.

Каждый контейнер для пользователя ведет себя почти как отдельная Linux-система 
(в нее можно зайти и как-то ею манипулировать), но, как правило, 
с одним запущенным процессом (например, Go или база данных).

Но при этом каждый контейнер использует одно общее ядро вашей ОС.
То есть, в отличие от виртуальных машин, контейнеры легковесные.

Далее картина становится такой:

(Слайд №5)

```text
Реальная ОС
    => группы контейнеров (каждая группа — это одно приложение)
        => внутри группы есть общая сеть, позволяющая им взаимодействовать.
```

Как правило, для управления каждой отдельной группой контейнеров используется 
Docker Compose.

Управлять им можно через специальный конфигурационный файл `compose.yaml`.

## compose.yaml

А теперь в контексте этого теоретического экскурса давайте посмотрим на нашу 
конфигурацию.

В корне есть файл `compose.yaml`.
В нем есть конфигурация для двух контейнеров — `api`, `postgres`.

Образ для сервиса `api` собирается по инструкции из файла 
`docker/go/Dockerfile`, а для базы данных используем готовый образ 
`postgres:18` из Docker Hub.

Для контейнера с базой мы определяем имя базы, имя юзера и пароль.
Далее стандартный порт и монтируем том `postgres_data` к контейнеру.

Выглядит это примерно так: когда контейнер стартует и том `postgres_data` 
еще не создан, Docker создает его и монтирует к директории `/var/lib/postgresql` 
контейнера.

То есть дальше контейнер `postgres` работает с файлами базы уже из тома 
`postgres_data`, который в упрощенном виде представляет директорию в 
нашей реальной ОС.

Также внутрь контейнера мы пробрасываем файлы из `./docker/postgres/init` 
в `docker-entrypoint-initdb.d`.

Там описаны дополнительные расширения, которые должны установиться с нашей СУБД 
`postgres`.

Теперь вернемся к контейнеру `api`.
Помимо файла с инструкцией по сборке образа (мы его посмотрим немного позже), 
определяется проброс портов.

То есть запрос на нашей реальной ОС на порт 8080 будет проброшен в контейнер 
тоже на порт 8080.
Далее мы указываем путь к файлу `.env`.

Это приведет к тому, что внутри контейнера будут доступны переменные окружения 
с именами, описанными в этом файле, и с указанными значениями.

Далее мы указываем, что при старте контейнера нужно пробрасывать все файлы 
с нашей ОС (из директории, в которой лежит `compose.yaml`) внутрь контейнера 
в директорию `/app`.

Также указываем, что хотим, чтобы этот контейнер зависел от контейнера 
`postgres`, то есть запускался после него (хотя это не гарантирует, 
что сама СУБД уже запустилась. 
Такая проверка будет, но мы придем к ней немного позже).

## Dockerfile

Теперь давайте посмотрим на Dockerfile, где описаны инструкции по сборке образа 
для контейнера `api`.

В сущности тут мы изначально берем готовый образ из Docker Hub, 
который уже имеет нужные файлы установленного на Debian 13 Go.

И далее по инструкции Dockerfile добавляем к образу новые слои.

1. Определяем рабочую директорию, в которой будет наше приложение.
2. Устанавливаем набор утилит, которые нужны нашему приложению.
3. Следующим отдельным слоем устанавливаем в контейнер утилиту `air`. 
Она нужна для того, чтобы не проводить ручную перекомпиляцию после изменения 
кода проекта. 
То есть без нее после каждого изменения кода нужно было бы перезапускать 
контейнер, а так это произойдет автоматически в фоне.
4. Далее устанавливаем утилиту для управления миграциями. 
Мы коснемся этой темы позже.
5. Следующим шагом мы добавляем директорию `/root/go/bin` в переменную `PATH` 
контейнера.
6. После этого определяем переменную `GOFLAGS` значением `-buildvcs=false`. 
Это нужно, чтобы Go не пытался встраивать в бинарный файл информацию 
о репозитории Git.
7. Далее мы копируем отдельным слоем файлы `go.mod` и `go.sum` и запускаем 
`go mod download`. 
Это нужно, чтобы при пересборке контейнера не тянуть все файлы используемых 
пакетов повторно. 
То есть это будет запускаться, только если изменился `go.mod` или `go.sum`.
8. Также мы копируем все файлы проекта в контейнер и указываем, 
что нужно запустить внутри контейнера `./docker/entrypoint.sh`.

Как результат, общий смысл заключается в том, что мы берем уже готовый образ 
и добавляем к нему свои слои. 
Каждый слой кэшируется и переделывается только в том случае, если в нем что-то изменилось.

На данный момент общая последовательность выглядит так:

(Слайд №6)

```text
docker compose up --build
    => Собирается образ api по инструкции docker/go/Dockerfile
    => Используется готовый образ postgres:18
    => Создаются контейнеры api и postgres
    => В контейнере api запускается ./docker/entrypoint.sh
```

## entrypoint.sh

Следующим шагом посмотрим на содержание этого sh-скрипта.
Этот скрипт не является обязательным. 
Он просто позволяет автоматизировать подготовку контейнера перед запуском приложения.

По сути, у него есть четыре основных действия:

1. Унифицировать владельца и права доступа к файлам между контейнером и хостовой ОС.
   Что это значит на практике?
   Как вы помните, мы пробрасываем файлы между нашим проектом на реальной ОС 
   и контейнером. 
   Так вот, это приведет к тому, что, если в контейнере создать файлы, 
   то они появятся в общем списке файлов проекта реальной/хостовой ОС, 
   НО станут принадлежать пользователю, от имени которого запущен процесс, 
   создавший эти файлы.
   То есть будут сложности с тем, чтобы работать с ними. 
   Это не критично, но неудобно.
   Поэтому в контейнере я создаю пользователя с таким же именем и ID, 
   как и у моего реального пользователя.
   Имя и ID пользователя я указываю в файле `.env`.
   И, если вы помните, мы его подключили в `compose.yaml` к контейнеру `api`.
   В общем-то, далее скрипт проверяет, что необходимые переменные окружения 
   существуют, и вызывает функцию `create_new_user`.

2. Далее мы ждем, пока не поднимется полностью PostgreSQL. 
Чтобы приложение не стало делать запросы к базе пока она полностью не запустилась.  

3. Выполняем миграции, если они есть.

4. Запускаем `air` от имени указанного пользователя.
   То есть внутри контейнера мы запустим `air`, а он будет следить за файлами 
   проекта и выполнять автоматически перекомпиляцию после каждого изменения. 
   Работать это будет на основе конфига, который мы сейчас тоже посмотрим.

## .air.toml

Конфигурация для `air` описана в файле `.air.toml`.

Здесь мы определяем, что рабочей директорией является корень проекта.

Далее указываем команду, которой нужно собрать приложение, и путь к полученному 
бинарному файлу, который затем будет запускаться.

Блок `args_bin` позволяет передать дополнительные аргументы запуска нашему 
приложению. 
В нашем случае он пустой, потому что сейчас они нам не нужны.

Также говорим `air`, что следить нужно только за файлами с расширением `.go`, 
а директории `.git`, `vendor`, `app/bin` и `docker` можно игнорировать, 
потому что изменения в них не требуют пересборки нашего приложения.

Параметр `delay` задает небольшую задержку перед запуском новой сборки. 
Это нужно, чтобы не начинать перекомпиляцию слишком часто, 
а дождаться, пока изменения закончатся.
То есть через три секунды после того, как изменения файлов кода прекратились.

Далее указываем, что перед запуском новой версии приложения предыдущий процесс 
нужно корректно остановить. 
Если процесс не завершится самостоятельно, то через `500ms` он будет принудительно остановлен.

И в самом конце включаем отображение времени в логах, чтобы было удобнее понимать, 
когда именно происходила сборка или запуск приложения.

В общем, ничего сложного здесь нет. 
Этот файл просто определяет, как именно должна работать утилита `air` во время разработки проекта.

## Стартовая структура проекта

Теперь давайте сделаем общий обзор файлов и директорий проекта на старте.

```text
├── bin
├── cmd
│   └── demo-api
│       └── main.go
├── compose.yaml
├── docker
│   ├── entrypoint.sh
│   ├── go
│   │   └── Dockerfile
│   └── postgres
│       ├── backup
│       └── init
│           └── 01-extensions.sql
├── go.mod
├── go.sum
├── .env
├── .env.debug
├── .env.example
├── internal
├── Makefile
├── migrations
├── README.md
└── remote
```

* `/bin` — тут будет скомпилированный бинарник нашего приложения.

* `/cmd/demo-api` — основные файлы приложения.

* `compose.yaml` — конфигурация сборки контейнеров.

* `/docker` — тут хранятся файлы, имеющие отношение исключительно к Docker, а не к приложению.

* `go.mod` — файл модуля проекта. На старте он содержит только имя модуля и версию Go.

* `go.sum` — контрольные суммы устанавливаемых пакетов.

* `.env` — это файл, содержащий набор ключей и значений, которые потом станут переменными окружения внутри контейнера. 
Если вы будете запускать этот проект на своих машинах, то перед стартом не забудьте изменить этот файл, а именно:

```text
DEMO_API_MAIN_SYSTEM_USER_ID=1000
DEMO_API_MAIN_SYSTEM_USER_NAME=vysmv
```

на идентификатор (ID) и имя пользователя вашей операционной системы.

Для пользователей Windows подойдут следующие значения:

`DEMO_API_MAIN_SYSTEM_USER_ID=0`
`DEMO_API_MAIN_SYSTEM_USER_NAME=root`

На macOS я не проверял, но думаю, что также подойдут значения, указанные для Windows.

* `.env.debug` — это аналогичный предыдущему файл, но подключается при запуске в режиме дебага. 

* `/internal` — директория, в которой будут наши вспомогательные пакеты.

* `Makefile` — файл автоматизации. Мы займемся им позже, когда дойдем до миграций.

* `/migrations` — директория с файлами миграций.

* `/remote` — директория с файлами, которые будут нужны при разворачивании проекта на сервере. Мы коснемся этого ближе к концу.

## Тестовый запуск

Думаю, что для старта этого описания проекта достаточно, и можно выполнить тестовый запуск.
В данный момент в `cmd/demo-api` есть файл `main.go`.
В нем простой код поднимающий веб-сервер и регистрирующий один обработчик — `healthcheckHandler`.
Давайте выполним команду для запуска наших контейнеров и убедимся, что все корректно работает:

```bash
docker compose up --build
```

Так вот, после выполнения запроса:

```bash
curl -X GET localhost:8080/v1/healthcheck
```

Мы должны увидеть результат вида:

```text
status: available
environment: dev
version: 1.0.0
```

На этом все и переходим к следующей теме.
