# HTTP-сервер и роутер

## main.go

После того как мы убедились, что у нас есть рабочее окружение и что все работает, как и ожидается, можно перейти к созданию HTTP-сервера.
Давайте переключимся на ветку `3-HTTP-server-and-router` и посмотрим на новый код.

Первым делом откроем файл `main.go`.
И проанализируем, что в нем изменилось?

1. Мы создаем строковую константу с номером версии нашего API.
2. Объявляем структуру конфига с двумя полями.
3. Объявляем структуру `app`, которая будет контейнером зависимостей приложения.
4. Объявляем экземпляр структуры `config` и считываем значения флагов командной строки в конфиг.
   
   Тут сделаю небольшое пояснение.
   Пакет `flag` позволяет считать значения, переданные в командной строке в момент запуска бинарника.
   Первым параметром мы передаем адрес, по которому нужно записать полученное значение, вторым идет имя флага, третьим — значение по умолчанию и четвертым — описание этого параметра.
   Далее, после компиляции, можно будет вызвать бинарник с флагом `--help` и увидеть описание всех флагов, которые принимает приложение.
5. Инициализируем новый структурированный логгер, записывающий сообщения в стандартный поток вывода.
6. Объявляем экземпляр структуры `app`, содержащий структуру `config` и `logger`.
7. Объявляем HTTP-сервер, который прослушивает порт, указанный в структуре `config`, использует в качестве обработчика маршрутизатор, который возвращает `app.routes()`, определяет настройки таймаутов и записывает все сообщения от веб-сервера через структурированный логгер с уровнем Error.
8. Запускаем HTTP-сервер.

## app.routes()

Следующим шагом посмотрим на метод `app.routes()`.
Этот метод возвращает маршрутизатор, который будет использовать наш веб-сервер.

Для этого проекта мы будем использовать сторонний пакет `httprouter`, а не `http.ServeMux` из стандартной библиотеки.
Для этого есть две основные причины:

1. Если происходит запрос на несуществующий маршрут (404 Page Not Found) или маршрут существует, но используется не тот метод (405 Method Not Allowed), то `http.ServeMux` по умолчанию отдает обычные текстовые ответы (не JSON).
   Хотя это поведение и можно изменить, но делается это немного замороченно.

2. `http.ServeMux` не обрабатывает по умолчанию запросы методом `OPTIONS`.

Поэтому для установки пакета я выполнил команду:

(Слайд №1)

```bash
go get github.com/julienschmidt/httprouter@v1
```

а значит, что далее могу использовать его в коде.

Если посмотреть на тело метода `app.routes()`, то станет понятно, что мы инициализируем новый экземпляр маршрутизатора `httprouter`.

Далее регистрируем для наших эндпоинтов маршрут, метод запроса и обработчик.
Для этого используется метод `router.HandlerFunc`, который третьим параметром принимает `http.HandlerFunc`.
Это специальный тип-адаптер, предназначенный для того, чтобы передавать функции как обработчики HTTP.

В конце просто возвращаем экземпляр маршрутизатора.

## app.healthcheckHandler

Теперь давайте посмотрим на метод `app.healthcheckHandler`.
На данном этапе метод крайне прост.
Он пишет в ответ статусную информацию о нашем API.

## movies.go

И теперь давайте посмотрим на два оставшихся хендлера.
Это `app.createMovieHandler` и `app.showMovieHandler`.

* `createMovieHandler` для эндпоинта `POST /v1/movies`. Пока что просто возвращает текстовый ответ-заглушку.
* `showMovieHandler` для эндпоинта `GET /v1/movies/:id`. На данном этапе получает параметр `id` из текущего URL и включает его в ответ-заглушку.

Тут стоит обратить внимание, что для получения параметра `id` используется вспомогательный метод `app.readIDParam(r)`.
Давайте на него посмотрим.

## helpers.go/app.readIDParam(r)

По смыслу тут происходит следующее: получаем параметр URL `id` из контекста текущего запроса, затем преобразуем его в целое число и возвращаем его. Если операция завершилась неудачно, возвращаем 0 и ошибку.

## Тестовые запуски

Теперь давайте выполним тестовые запуски, чтобы убедиться, что все работает так, как мы и ожидаем.

Перед тем как запускать, на всякий случай уточню: несмотря на то, что мы используем `air`, который автоматически выполняет перекомпиляцию бинарника, нужно всё-таки пересобирать контейнеры после установки пакета.
То есть сначала остановить контейнеры через `Ctrl+C`, а потом выполнить:

```bash
docker compose up --build
```

Первым делом после окончания сборки давайте посмотрим на описание флагов, которые может принимать приложение.
Для этого запустим наш бинарник с аргументом `--help`:

```bash
./bin/demo-api --help
```
И увидим, что на данном этапе приложение способно принимать два флага.

И в качестве дополнения отмечу, что передавать флаги можно в одном из следующих форматов:

(Слайд №2)
```bash
./bin/demo-api --port=9090 --env=development
./bin/demo-api -port=9090 -env=development
./bin/demo-api --port 9090 --env development
```

Но так как мы запускаем бинарный файл не вручную, а через `air`, флаги можно передавать в конфигурационном файле `.air.toml`.

Как я говорил ранее, это делается в секции `args_bin`.

Теперь проверим наши эндпоинты.
Начнем с `healthcheck`:

```bash
curl localhost:8080/v1/healthcheck
```

Как результат, увидим ответ со статусной информацией:
```text
status: available
environment: development
version: 1.0.0
```

Далее сделаем запрос на эндпоинт для создания фильма:

```bash
curl -X POST localhost:8080/v1/movies
```

И, как и ожидается, увидим текст-заглушку:

```text
create a new movie
```

Далее выполним запрос на получение информации об одном фильме:

```bash
curl localhost:8080/v1/movies/123
```

В этом случае мы снова увидим текст-заглушку, но уже с переданным нами `id`:

```text
show the details of movie 123
```

Далее выполним проверку запроса к существующему маршруту, но с использованием другого метода:
```bash
curl -i -X POST localhost:8080/v1/healthcheck
```
Увидим, что поддерживаются методы: `GET`, `OPTIONS`.

В качестве ответа получим `Method Not Allowed` и код `405`.

И да, по умолчанию мы также получим обычный текстовый ответ с `Content-Type: text/plain; charset=utf-8`, но изменить это поведение очень легко, и дальше мы это сделаем.

Далее выполним запрос методом `OPTIONS`:
```bash
curl -i -X OPTIONS localhost:8080/v1/healthcheck
```
И тоже получим корректную информацию.

В завершение проверим запрос к несуществующему маршруту:
```bash
curl -i localhost:8080/v1/movies/abc
```
И увидим, что в этом случае всё тоже отработало корректно.

## Резюме

Мы посмотрели все изменения этого этапа, и пришло время подвести итоги.

Итак, сейчас у нас есть:

* контейнер с зависимостями `app`;
* веб-сервер со сторонним маршрутизатором `httprouter`;
* набор зарегистрированных эндпоинтов в этом маршрутизаторе.

(Слайд №3)
| Метод | Шаблон URL        | Обработчик           | Действие                                |
| ----- | ----------------- | -------------------- | --------------------------------------- |
| GET   | `/v1/healthcheck` | `healthcheckHandler` | Показать информацию о приложении        |
| POST  | `/v1/movies`      | `createMovieHandler` | Создать новый фильм                     |
| GET   | `/v1/movies/:id`  | `showMovieHandler`   | Показать информацию о конкретном фильме |

Все обработчики являются методами структуры `app`.

* Есть файл `helpers.go`, в котором пока находится один вспомогательный метод `readIDParam`, тоже реализованный как метод структуры `app`.
  И хотя сейчас он не использует никаких зависимостей, такой подход удобен с перспективой развития.
  На какой-то из следующих итераций развития проекта может понадобиться какая-то зависимость.

Также в качестве дополнения отмечу, что при использовании маршрутизатора `httprouter` недопустимы конфликтующие маршруты.
Например, нельзя зарегистрировать маршруты вида:

(Слайд №4)
```text
GET /foo/new
и 
GET /foo/:id
```
Но при использовании стандартной REST-структуры это не станет проблемой, а, напротив, даже будет преимуществом.
Поскольку конфликтующие маршруты запрещены, вам не нужно беспокоиться о правилах приоритета маршрутизации.

На этом всё, и переходим к следующему блоку.
