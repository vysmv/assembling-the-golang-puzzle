# Разбор JSON-запросов

А теперь давайте посмотрим, как читать JSON-запросы, пришедшие от клиента.
Для этого переключимся на ветку `5-Parsing-JSON-requests` и посмотрим, что изменилось в нашем проекте.

Итак, у нас есть эндпоинт `POST /v1/movies` и обработчик `createMovieHandler`.

Так вот, когда клиент обращается к этому эндпоинту, мы ожидаем, что он передаст JSON-тело запроса, содержащее данные фильма. Например, если клиент хочет добавить в наше API запись о фильме Moana, он отправит тело запроса, примерно с такими данными:

(Слайд №1)
```json
{
    "title": "Moana",
    "year": 2016,
    "runtime": 107,
    "genres": ["animation", "adventure"]
}
```

Следующий важный момент который нужно понять на старте, это то что, как и в случае с кодированием в JSON, существует два подхода для декодирования JSON в нативное значение Go: использование типа `json.Decoder` или функции `json.Unmarshal()`.

И в этот раз мы будем использовать именно `json.Decoder`.

Также давайте сразу разберем вопрос о том, какие нативные типы Go подходят для целевого декодирования из JSON.
Для этого можем посмотреть на следующую таблицу:

(Слайд №2)

| Тип JSON     | ⇒ | Поддерживаемые типы Go              |
| ------------ | - | ----------------------------------- |
| JSON boolean | ⇒ | `bool`                              |
| JSON string  | ⇒ | `string`                            |
| JSON number  | ⇒ | `int*`, `uint*`, `float*`, `rune`   |
| JSON array   | ⇒ | массив (`array`), срез (`slice`)    |
| JSON object  | ⇒ | структура (`struct`), карта (`map`) |

В принципе тут все довольно-таки просто и интуитивно понятно, так что можем идти дальше.

## cmd/demo-api/movies.go createMovieHandler

Далее откроем файл `cmd/demo-api/movies.go` и перейдем к методу `createMovieHandler()`.

Тут нас ждет несколько нововведений. Давайте на них посмотрим.

1. Объявляем анонимную структуру для хранения информации, которую мы ожидаем получить в теле HTTP-запроса (обратите внимание, что имена и типы полей этой структуры являются подмножеством структуры `Movie`, которую мы объявили ранее).
   Эта структура будет нашей *целевой структурой для декодирования*.
   Также стоит обратить внимание на то, что для поля `Runtime` снова указан именованный тип `data.Runtime`. Мы этого коснемся немного позже.

Тут, конечно, может возникнуть вопрос: почему нужна промежуточная структура?

Проблема в том, что, если декодировать напрямую в `Movie`, клиент сможет передать в JSON поля `id` и `version`, и их значения будут успешно записаны в поля `ID` и `Version` структуры `Movie`, хотя мы этого совсем не хотим.

Конечно, после декодирования можно было бы отдельно проверять, что эти поля пусты, но такой подход выглядит довольно неуклюжим. Использование промежуточной структуры — более чистое, простое и надежное решение, пусть и немного более многословное.

2. Используем новый метод-помощник `readJSON()` для декодирования тела запроса в структуру `input`.
   Если возникнет ошибка, отправляем клиенту сообщение вместе со статусом `400 Bad Request`, используя для этого еще один новый метод `app.badRequestResponse`.

3. Копируем значения из `input` в новую структуру `Movie`.

4. Создаем новый экземпляр `Validator`.

5. Вызываем `ValidateMovie()`. Если есть ошибки, возвращаем их клиенту.

6. Пишем в ответ нашу структуру `input`.

То есть, по сути, мы просто считываем входящие данные через `app.readJSON()` в промежуточную анонимную структуру.
Далее из анонимной структуры копируем полученные данные в структуру `Movie`.
После чего валидируем эти данные и, если все ок, то пишем их же в ответ.

А теперь давайте посмотрим на детали. 

## internal/data/runtime.go

Первым делом откроем файл `internal/data/runtime.go`, чтобы посмотреть, зачем мы используем именованный тип в структуре, принимающей данные из запроса.

Мы видим, что для типа `Runtime` появился метод `UnmarshalJSON()`.
Суть его аналогична методу `MarshalJSON()`, только наоборот.
То есть он будет вызван в тот момент, когда будет происходить декодирование значения из JSON в значение этого типа.

- В запросе это поле будет представлять собой строку формата `"<runtime> mins"`.
  А значит, сначала необходимо удалить окружающие двойные кавычки.
  Если это не удается сделать, возвращаем ошибку `ErrInvalidRuntimeFormat`, которая объявлена вверху этого файла.
- Далее разбиваем строку, чтобы отделить числовую часть.
- Потом проверяем, что строка имеет ожидаемый формат. Если нет — снова возвращаем `ErrInvalidRuntimeFormat`.
- Преобразуем строку с числом в `int`. Если преобразование не удалось, также возвращаем `ErrInvalidRuntimeFormat`.
- И в завершение преобразуем `int` в тип `Runtime` и изменяем значение ресивера.

По смыслу этот функционал также не обязательный, а просто демонстрирует возможность самостоятельно определить, как будет происходить декодирование значения.

Переходим к следующему вопросу.

## cmd/demo-api/helpers.go readJSON


Для этого вернемся к методу `createMovieHandler` и откроем вспомогательный метод `readJSON()`.

Давайте посмотрим на его функционал:

1. Используем `http.MaxBytesReader()`, чтобы ограничить размер тела запроса до 1 048 576 байт (1 МБ).
2. Создаем `json.Decoder` и вызываем метод `DisallowUnknownFields()` перед декодированием.
   Благодаря этому, если JSON содержит поле, которое невозможно сопоставить с целевой структурой, декодер вернет ошибку вместо того, чтобы просто проигнорировать это поле. То есть мы отклоняем запросы с данными которые мы не ожидаем.
3. Декодируем тело запроса.
4. Далее объявляем набор переменных для разделения ошибочных ситуаций.

Тут сделаю небольшое теоретическое отступление.

Есть пять типов ошибок, которые мы можем получить при декодировании:

(Слайд №3)

| Ошибка                                     | Причина                                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `json.SyntaxError` и `io.ErrUnexpectedEOF` | В декодируемом JSON присутствует синтаксическая ошибка.                                                                              |
| `json.UnmarshalTypeError`                  | Значение в JSON не подходит для целевого типа Go.                                                                                    |
| `json.InvalidUnmarshalError`               | Указана недопустимая цель декодирования (обычно потому, что передан не указатель). Это проблема нашего приложения, а не самого JSON. |
| `io.EOF`                                   | Декодируемый JSON пуст.                                                                                                              |


Именно на основе этих ошибок мы создаем свои переменные, позволяющие отличить одну ошибочную ситуацию от другой.
Так вот, далее по коду в секции `switch` мы проверяем, какая из этих ошибок случилась, и даем внятное описание, не раскрывающее подробности того, как работает API.

Тут же мы отслеживаем ошибку, сигнализирующую о том, что тело запроса больше одного мегабайта.

Отдельно еще стоит упомянуть ошибку `invalidUnmarshalError`, в результате которой мы генерируем панику.
Такое решение принято вследствие того, что эта ошибка может произойти только по вине программиста, когда в `Decode()` передали неподдерживаемое значение в качестве цели декодирования.

И в самом конце мы делаем еще одну проверку, блокирующую отправку в запросе больше одного JSON-значения.

## cmd/demo-api/errors.go app.badRequestResponse

Если теперь снова вернуться к методу `createMovieHandler`, то увидим, что далее требует разбора новый метод `app.badRequestResponse`.

Давайте перейдем в файл `cmd/demo-api/errors.go` и посмотрим на него.

По смыслу это просто обертка, которая определит код ответа `400 Bad Request` и вызовет метод `app.errorResponse`, чтобы записать ответ клиенту.

## internal/validator/validator.go

Следующим новым функционалом является добавление валидации входящих данных.

Валидация реализована по следующему принципу:

1. Мы создаем экземпляр валидатора. Давайте посмотрим на его устройство, перейдя в файл `internal/validator/validator.go`.

   Как вы видите, это отдельный пакет.

   - В начале мы объявляем регулярное выражение для базовой проверки формата адресов электронной почты.
   - Далее определяем новый тип `Validator`, содержащий карту ошибок валидации.
   - Потом объявляем функцию, создающую новый `Validator` с пустой картой ошибок.
   - Также тут есть метод валидатора `Valid()`, который проверяет, есть ли в `map` валидатора ошибки.
   - И метод `AddError()`, который добавляет сообщение об ошибке в карту.
   - Следующим идет метод, который позволяет выполнить валидацию. `Check()` добавляет сообщение об ошибке, если проверка не прошла.
   - А в конце три утилитарные функции:
     - `PermittedValue()`, возвращающая `true`, если значение содержится в списке допустимых значений.
     - `Matches()`, возвращающая `true`, если строка соответствует регулярному выражению.
     - `Unique()`, возвращающая `true`, если все значения в срезе уникальны.

Теперь снова вернемся в метод `createMovieHandler()`.

2. И видим, что далее идет вызов метода `data.ValidateMovie()`, которому передаем экземпляр валидатора и переменную `movie`.

   Давайте посмотрим на этот метод.

   Тут тоже все просто: в этом методе собран набор проверок именно для типа `Movie`.

   То есть происходит множественный вызов метода валидатора `Check()`, и, если условие в первом аргументе не удовлетворяется, в валидатор добавляются ключ и текст ошибки.

   Также тут можно увидеть использование одной из утилитарных функций пакета `validator` — `Unique()`.
   Она используется для проверки того, что все указанные жанры уникальны.

И если снова вернуться в `createMovieHandler()`, то увидим, что далее просто вызывается метод `v.Valid()`.

А если валидация прошла успешно, то карта ошибок будет пустая.

Если подрезюмировать этот функционал, то все просто и логично.

Есть пакет `validator` и есть метод `ValidateMovie()`, который содержит набор проверок для структуры `Movie`, реализованных при помощи функционала этого пакета.

Всё.

И если валидация не пройдена, то будет вызван еще один вспомогательный метод для обработки ошибок — `app.failedValidationResponse()`.

В сущности он просто устанавливает код `422 Unprocessable Entity` и передает `map` ошибок валидатора методу `app.errorResponse`, чтобы записать их в JSON-формате в ответ клиенту.

## Тестовые запуски

А теперь давайте сделаем ряд запросов, чтобы убедиться, что все работает так, как мы и ожидаем.

1. Для начала отправим XML в качестве тела запроса.
```bash
curl -d '<?xml version="1.0" encoding="UTF-8"?><note><to>Alex</to></note>' localhost:8080/v1/movies
```
Получаем в ответ ошибку из нашего `switch`:
```json
{
        "error": "body contains badly-formed JSON (at character 1)"
}
```

2. Отправляем некорректный JSON (обратите внимание на завершающую запятую):
```bash
curl -d '{"title": "Moana", }' localhost:8080/v1/movies
```

И получаем также наше сообщение об ошибке:
```json
{
        "error": "body contains badly-formed JSON (at character 20)"
}
```

3. Отправляем JSON-массив вместо объекта:
```bash
curl -d '["foo", "bar"]' localhost:8080/v1/movies
```

И снова получаем наше сообщение об ошибке:
```json
{
        "error": "body contains incorrect JSON type (at character 1)"
}
```

4. Делаем запрос с размером тела более одного мегабайта (тело запроса берется из файла в корне):
```bash
curl -d @./largefile.json localhost:8080/v1/movies
```

Как и ожидалось, снова получаем текст ошибки:
```json
{
        "error": "body must not be larger than 1048576 bytes"
}
```

5. Также давайте проверим работу валидации, выполнив следующий запрос:
```bash
BODY='{"title":"","year":1000,"runtime":"-123 mins","genres":["sci-fi","sci-fi"]}' &&  curl -i -d "$BODY" localhost:8080/v1/movies
```

Это приведет к ответу с кодом `422 Unprocessable Entity` и телом с переченем ошибок:
```json
{
        "error": {
                "genres": "must not contain duplicate values",
                "runtime": "must be a positive integer",
                "title": "must be provided",
                "year": "must be greater than 1888"
        }
}
```

6. И напоследок выполним корректный запрос для создания фильма:
```bash
BODY='{"title":"Moana", "year": 2016, "runtime":"107 mins", "genres":["animation","adventure"]}' && curl -d "$BODY" localhost:8080/v1/movies
```

В этом случае получим, корректный ответ:
```json
{Title:Moana Year:2016 Runtime:107 Genres:[animation adventure]}
```
